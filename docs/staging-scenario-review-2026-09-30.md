# 스테이징에서 시나리오 기반 재난대응을 검토하는 방안

작성: Codex / 2026-09-30 / Asia/Seoul

상태: 사용자 요청에 따른 재검토 및 Claude 인계 문서. 이번 작업은 문서 작성이며, 스테이징 생성·앱 기능 구현·커밋·푸시·배포 완료를 뜻하지 않는다.
검토 기준: 로컬 HEAD `b558e23` 및 현재 미커밋 변경을 포함한 코드. `git pull --rebase origin master`는 미커밋 변경 때문에 실행되지 않았다. 기존 변경을 stash·초기화·덮어쓰기하지 않았다. 배포 사이트를 직접 시험한 결과가 아니라 코드 대조 결과다.

## 1. 사용자가 확인한 방향

사용자는 기존 사이트와 별도로 스테이징에서 시나리오를 실행하고, 대시보드를 보며 재난대응 흐름을 검토하는 방향에 동의했다.

- 실시간 운영 데이터는 **기상청 동네예보만 사용**한다.
- 나머지 관측·사건·영향·인력·장비 데이터는 모의 데이터로 준비한다.
- 사용자가 입력하는 서비스별 시간별 수치가 바뀌면, 관련 모의 데이터와 화면도 함께 바뀌어야 한다.
- 사용자는 업로드 후 통합/서비스 대시보드에서 수치·등급·판단 근거를 확인하고, 경보·출동·자원·종료 절차를 직접 진행한다.
- 고정된 데이터 항목을 유지하면서 시나리오별 수치만 바꾸고 싶다는 기존 요구를 유지한다.

기존 합의도 유지한다: 첫 구현 검증은 **하천범람 파일럿**, 입력은 **돈내코·쇠소깍의 Q%(계획홍수량 대비 비율)**, 수집상태 엑셀과 시나리오 엑셀은 별도 파일이다. 하향은 시나리오 시계 기준 30분 유지 후 한 단계씩, 관측 사이에는 직전 값 유지, 정상 종료는 유지시간·조치 완료·자원 복귀·사용자 확인을 거친다. 예외 강제 종료는 구분해서 기록한다.

이번의 전체 서비스 모의 데이터 방향은 확장 목표다. 기존 하천 파일럿의 입력에 수위·강우·AI 조기경보를 한꺼번에 추가하는 승인으로 해석하지 않는다. 나머지 서비스를 같은 수준으로 완성하는 것은 후속 단계로 제안한다.

## 2. 재검토 결론

**하나의 코드 저장소에서 기존 사이트와 스테이징의 배포 설정·데이터 모드를 분리하고, 스테이징에 재현 가능한 시나리오 실행 상태를 두는 방안이 적합하다.** 현재 하천 실행 상태·구독·대응 명령은 재사용할 수 있다. 사이트 주소를 하나 더 만드는 작업만으로 시나리오와 모든 화면이 동기화되지는 않는다.

동기화의 기준은 `시나리오 입력 + 현재 시나리오 시각 + 모의 규칙 + 사용자가 수행한 조치`다. 카드·목록·지도·그래프·브리핑·결재함이 각자 별도의 숫자를 갖지 않도록 한다.

임의 데이터는 화면을 새로 열 때마다 난수로 생성하지 않는다. 같은 입력·모의 규칙·조작을 재실행하면 같은 수치·등급·대응 결과가 나와야 검토 전후를 비교할 수 있다. 실행 식별자인 `runId`가 새로 만들어지는 것은 재현성과 별개다. 실시간 동네예보는 조회할 때 바뀔 수 있으므로 모의 결과의 재현성 비교에서 제외하고, 초기 단계의 모의 결과 계산에도 넣지 않는다.

현재 정상 종료 검사는 `closurePending`을 읽고, 그 계산은 지점의 정상 여부와 자원 복귀 여부를 사용한다. 관측되지 않은 지점을 정상으로 취급할 수 있는지, 정상 유지 30분 및 조치 완료를 충분히 검사하는지는 스테이징 완료 기준으로 별도 확인한다. 기존 종료 정책이 모두 구현됐다고 단정하지 않는다.

이 문서의 제안 파일명·설정명은 아직 구현된 것이 아니다. 이후 작업에서는 미커밋 수정과 최신 코드를 다시 확인한다.

## 4. 배포 환경과 데이터 환경

권장안은 기존 저장소를 유지하고, 스테이징 프런트엔드를 **별도 호스팅 프로젝트와 별도 origin**에 배포하는 것이다. origin은 주소의 프로토콜·호스트·포트 조합이다. 실제 호스팅 제공자와 주소는 미정이다.

GitHub Pages는 저장소당 프로젝트 사이트 하나를 제공한다. 같은 저장소의 배포 환경 이름을 `staging`으로 바꾸는 것만으로 독립 Pages 사이트가 추가되지는 않는다. GitHub Pages만 사용하려면 별도의 배포용 저장소를 검토할 수 있다. [GitHub Pages 공식 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

**같은 계정의 Pages 저장소를 하나 더 만들면 기본 주소는 경로만 달라지고 origin은 같을 수 있다.** `localStorage`는 origin 단위이고 `BroadcastChannel`도 같은 origin의 창 사이에서 통신하므로, 주소 경로가 다르다는 이유만으로 운영/스테이징 상태가 분리된다고 가정하지 않는다. 이 결론은 Pages 기본 주소 형식과 브라우저 저장/통신 범위를 대조한 설계 판단이다. [localStorage 범위](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage), [BroadcastChannel 범위](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)

스테이징 설정의 제안 예시:

| 항목 | 기존 사이트 | 스테이징 |
| --- | --- | --- |
| 앱 환경(예: `VITE_APP_ENV`) | production | staging |
| 데이터 모드(예: `VITE_DATA_MODE`) | 기존 데이터 정책 | simulation |
| 표시 | 기존 표시 | `스테이징 · 모의 재난대응` 상시 표시 |
| 배포 대상 | 현재 GitHub Pages | 별도 주소/프로젝트 |
| 브라우저 저장 키·통신 채널 | 기존 키 호환 | 스테이징 전용 prefix |
| 일치 검사 | 현재 정책 | 스테이징 진단용 설정으로 활성화 |

`vite build --mode staging`은 사용 가능하지만, staging 모드라는 이유로 `import.meta.env.DEV`가 true가 되지는 않는다. 별도 설정을 읽어 데이터 정책과 진단을 결정한다. 현재 `.gitignore`는 `.env.*`를 제외하므로 환경 설정 예시는 추적 가능한 예제 파일이나 문서에 남긴다. 공개 `VITE_*` 값에는 앱 모드·프록시 URL만 두고, 기존 API 서비스키는 서버 프록시에 유지한다. [Vite 환경변수와 모드](https://vite.dev/guide/env-and-mode)

저장 키 분리 대상은 하천 실행(`jeju-ax-river-run`), 수집 엑셀(`jeju-ax-dummy-workbook`), 시나리오 선택(`jeju-ax-scenario`), 데모 로그인(`jeju-ax-session`)이며 하천 BroadcastChannel 이름도 분리한다. 기존 사이트의 저장값을 스테이징으로 자동 가져오지 않는다. 상세 창 이름도 필요하면 환경별로 구분한다.

| KHOA 스냅샷 | 실제 스냅샷은 스테이징 시험 상태에 주입하지 않음. 필요 항목은 별도 모의 관측으로 준비 | 모의 값을 `실측`·`스냅샷` 태그로 표시하지 않음 |
| 센서 수집상태·장애 | 기본 정상 모의 상태, 필요하면 별도 수집 엑셀/장애 사건으로 변경 | 정상·지연·오류·누락은 위험등급과 별개 |
| 담당자·인력·장비·시설 | 고정된 모의 기본 목록 자동 준비 | 실제 시험 명령에 따라 가용·요청·투입·복귀 상태 갱신 |
| 지리 대상지·임계값·SOP·공식 사업 계획 | 확정 사실 그대로 유지 | 위험판정 기준이나 확정 규모를 임의 데이터로 바꾸지 않음 |

여기서 '동네예보만 실데이터'는 재난 관측·발표·사건 데이터에 적용한다. 지도 배경 타일과 확정된 정책 문서·대상지 정보까지 가상으로 바꾸자는 뜻으로 해석하지 않는다. OSM/Esri 지도 타일은 배경으로 유지하는 방안을 제안한다. 외부 네트워크 요청을 전부 하나로 제한하려는 요구가 생기면 지도 정책은 별도 조정한다.

실 API 모듈/공통 공급 경로에서 스테이징 호출 제한을 적용하고, 보드·상세 화면 모두 같은 모의 공급자를 사용한다. UI에서 패널 하나를 숨기는 것만으로 실호출 차단을 완료 처리하지 않는다. 모의 값이 없다고 실제 API로 자동 전환하지 않는다. 동네예보 오류는 오류/조회 불가로 표시하고, 모의 예보를 실제 응답처럼 대신 표시하지 않는다.

현재 실 API 컴포넌트 및 `Card`·`Group`의 제목·subtitle·`source={LIVE}`도 함께 점검한다. 데이터 수집의 출처 목록, 데이터 시스템, 모니터링, `/pilot-status`에는 실제 연동 가능 현황과 '이 스테이징에서 현재 모의로 사용 중'인 상태를 구분한다. 실증 가능 현황 문서 자체를 가짜 연동 사실로 다시 쓰지 않는다.

## 6. 시나리오 수치와 주변 모의 데이터의 연결

입력과 결과는 아래 순서로 연결한다.

1. 고정된 대상지·센서·시설·모의 인력·장비 목록을 준비한다.
2. 사용자가 시나리오 엑셀을 업로드하면 검증한 입력과 모의 규칙 버전을 실행에 묶는다.
3. 현재 시나리오 시각까지의 관측을 적용한다. 최초 관측 전은 `관측 없음`, 이후 관측 사이에는 직전 값을 유지한다.
4. 확정된 서비스 기준으로 원본 수치의 후보 등급을 계산하고, 하향 유지 정책을 적용한 현재 운영 등급을 구분한다.
5. 현재 수치·운영 등급에 해당하는 모의 영향·점검 항목·대응 권고·경보 초안을 생성한다.
6. 사용자의 확인·승인·출동·복귀 명령과 선택된 모의 응답을 적용한다.
7. 같은 실행 상태를 카드·지도·분석·브리핑·결재함·대응 현황에 표시한다.

모의 기본 목록은 사용자가 수기로 전부 채울 필요가 없다. 기존 대상지 이름과 역할은 재사용하고, 시험용 센서 ID·시설·가상 자원 수량은 코드의 고정 기본 세트로 준비한다. 지표가 하나인 하천 파일럿은 기존 지점 키를 유지한다. 다중 지표를 추가할 때 서비스·지점·지표의 안정적인 식별자를 도입하고 단위/필수 여부를 함께 관리한다.

보조 값별 생성 규칙:

| 보조 데이터 | 권장 연결 방식 |
| --- | --- |
| 면적·인구·시설 영향 | 지점별 고정 모의 시설/구역 목록에 등급별 영향 대상을 지정하고, 선택된 대상에서 목록·합계를 계산 |
| 대피 경로 | 모의 경로 목록의 이용 가능/통제 조건을 시나리오 사건에 연결. 실제 최적경로 계산으로 표시하지 않음 |
| 대응 권고·필요 인력 | 서비스 SOP와 모의 배치 규칙으로 권고량 계산 |
| 가용/배치 인력·장비 | 고정 보유량과 승인된 요청에서 계산. 등급 상승만으로 자동 배치하거나 보유량을 늘리지 않음 |
| CCTV 확인·교차검증 | 모의 사건/센서 세트에 관측 시각·결과를 연결. 실제 영상 분석이나 실제 센서 측정이라고 표시하지 않음 |
| 수집상태·품질 | 기본 정상값 또는 명시적 장애 사건/수집 엑셀에서 읽음. 재난 등급만으로 통신 장애를 만들지 않음 |
| 경보·출동·종료 이력 | 시험 중 수행한 사용자 명령과 그에 따른 모의 응답으로 생성. 승인 당시 수치/등급/시각은 보존 |

**Q%에서 수위(m)·강우(mm)·조위(m)·영향 인원을 물리적으로 역산하지 않는다.** 필요하면 시나리오 기본 세트의 별도 모의 시계열 또는 '모의 영향 규칙'을 명시해 채운다. 처음에는 하천 Q%의 판정 입력을 그대로 유지하고, 영향/시설/자원/확인 자료부터 연결하는 편이 범위가 작다. 수위·강우 그래프까지 시험하고 싶다면 별도 모의 시계열 공급을 후속 작업으로 명시한다.

실제 관측이 없다는 이유만으로 화면 전체를 비워둘 필요는 없다. 스테이징에서는 준비된 모의 영향·확인 자료를 표시하되, 자료가 없는 경우에는 `미제공`으로 표시한다. 미관측을 0·정상으로 표시하지 않는다. AI 신뢰도를 임의 백분율로 채우는 경우도 모의 설정값임을 밝혀야 하며 실제 예측 정확도로 설명하지 않는다.

## 7. 시간·입력·값 소유권

- 시나리오 시계는 실시간 헤더 시계와 구분한다. 화면에 실행 ID·현재 시나리오 시각·진행/일시정지 상태를 표시한다.
- 실시간 동네예보는 별도의 실제 시각을 갖는다. 과거 시나리오를 재생할 때 현재 예보를 과거의 관측 근거로 사용하지 않는다.
- 그래프/근거에는 현재 시점까지 적용된 값만 표시한다. 엑셀의 미래 행을 예측값이나 현재 감지 결과로 미리 노출하지 않는다.
- 현재 `advance()`는 행 하나씩 진행한다. 같은 시각의 돈내코·쇠소깍 행을 한 시점으로 함께 적용하는 방식과, 값이 없는 구간의 시계 진행/예약 사건 처리를 검토한다. 현재 구현을 이미 시각 단위 일괄 처리한다고 설명하지 않는다.
- 자동 재생은 하나의 실행 제어자가 시간을 진행하도록 하고, 다른 보드/상세 창은 그 상태를 구독한다. 여러 창에서 타이머가 중복 진행하지 않아야 한다.
- 마지막 관측 이후에도 정상 유지/모의 도착/복귀 검증에 필요한 시간이 있다. 시계만 진행하는 기능 또는 충분한 종료 구간 입력을 마련하고 정책 충족 여부를 명시한다. 현재 예약 도착 처리는 다음 관측 진행 시점에서 확인된다.
- 날짜값은 기존 Excel UTC 표시 시각 처리 방식을 유지한다. 빈 Q%를 0으로 읽지 않고, 유효한 날짜·시간을 검증/정규화한 뒤 중복 검사와 정렬을 한다. 현재 시계열 파서는 문자열 형태만 검사하고 `Number("")`가 0이 될 수 있어 보완 대상이다.
- 파일 전체를 검증한 뒤 새 실행으로 교체한다. 검증 실패 시 기존 실행을 유지하고, 재업로드/초기화는 새 실행 상태와 새로운 모의 결과를 함께 준비한다. 종료된 실행은 시간 진행·승인 명령으로 다시 변경되지 않아야 한다.

수집 엑셀은 수집상태·품질·장비 기본 현황의 소유자이고, 시나리오 실행은 위험판정 수치·등급·영향 결과의 소유자다. 기존 수집 엑셀에 들어 있는 표시용 수치를 시나리오의 최신 관측값으로 오인하지 않게 구분한다. 동일 항목의 위험 수치를 두 공급자가 덮어쓰지 않도록 한다. 수집 파일에 없는 서비스의 목록을 비우지 않는 기존 보호도 유지한다.

초기화 순서는 `환경 설정 → 고정 모의 기본 목록/수집 설정 → 저장 실행 복원 → 현재 시점 투영 → 화면 구독`처럼 명시하는 방안을 권한다. 현재 `main.tsx`의 import 부작용과 본문 실행 순서에 의존하는 구조는 실제 순서를 재확인한 뒤 정리한다. 저장 시나리오 절대 시각에 `scenarioClock.ts`의 현재시각 평행이동을 중복 적용하지 않는다.

## 8. 하천 첫 검토 사례

다음은 상승 구간 예시다. Q%와 등급 경계는 현재 `classifyRiverRisk()` 기준이며, 모의 영향의 실제 숫자는 아직 정하지 않았다.

| 시나리오 시각 | 돈내코 Q% | 후보/상승 시 운영 등급 | 연동해서 확인할 결과 |
| --- | --- | --- | --- |
| 09:00 | 18 | 정상 | Q%·관측시각 표시, 모의 기본 시설·가용 자원 확인 |
| 09:10 | 35 | 관심 | 점검 권고, 관련 모의 시설/확인 자료 변경 |
| 09:20 | 55 | 주의 | 모의 영향 목록/합계, 경보 초안·대응 권고 확인 |
| 09:30 | 75 | 경계 | 영향 확대 규칙, 배치 권고, 사용자 요청·승인 |
| 09:40 | 105 | 심각 | 카드·지도·근거 일치, 자원 중복/가용량 검사 |

쇠소깍은 별도 행으로 다른 수치를 줄 수 있다. 등급 하향 검토에는 각 단계의 30분 유지 구간을 충분히 넣고, 후보 등급과 유지 중인 운영 등급을 함께 설명한다. 현장 대응 후 정상 종료를 확인하고, 별도의 시험에서는 강제 종료→동일 파일 재업로드→새 실행도 확인한다.

시험에서의 작업 흐름은 `시나리오 관리 화면에서 업로드/시점 진행 → 대시보드에서 수치·등급·근거 검토 → 상세 화면에서 경보/자원 대응 → 대시보드에서 결과 확인 → 종료 확인`이다. 시나리오 관리 화면의 성공만으로 전체 검토를 완료하지 않는다.

## 9. 최소 구현 순서 제안

1. **환경 분리**: 별도 배포 대상·base·staging/simulation 설정·표시·저장 키/채널·스테이징 진단을 준비한다. 기존 사이트 모드도 함께 검증한다.
2. **실호출 분리**: 동네예보만 허용하고 나머지 데이터 공급을 공통 모의 경로로 전환한다. 보드와 상세 화면의 출처/제목도 일치시킨다.
3. **하천 모의 기본 세트**: 고정 시설·구역·경로·센서/CCTV 확인 자료·가상 자원을 준비하고, Q% 등급별 모의 영향/권고 규칙을 문서화한다.
4. **화면 동기화**: 기존 실행 상태에서 주변 모의 결과를 계산해 상황 분석의 영향·확인 자료·대응 권고와 대시보드·브리핑에 같은 값으로 표시한다.
5. **시간/대응 검증**: 실제 재생 동작·동일 시각 처리·종료 조건·강제 종료 후 재실행·새로고침/별도 창을 끝까지 검증한다.
6. **다른 서비스 확대**: 하천 검토가 끝난 뒤 저염분수·고수온, 연안, 호우, 태풍, 폭염의 입력/규칙을 순차 연결한다. 다른 서비스는 그 전까지 '기본 모의 상태·해당 시나리오 미선택'을 표시한다.

기존 `riverRunState.ts`와 작은 계산/공급 함수로 시작한다. 모든 서비스를 위한 대형 상태관리 체계나 새 백엔드를 먼저 만들 필요는 없다. 코드/화면 보완을 스테이징에서 검토한 뒤 기존 사이트에 반영할 때는 데이터 모드와 배포 설정을 함께 검사한다.

## 10. 완료 확인 기준

아래 항목은 **후속 구현의 검증 기준**이다. 이번 문서 작업에서 통과했다고 보고하는 항목이 아니다.

- 스테이징 모든 관련 화면을 방문해 네트워크 요청을 확인한다. 운영 관측 API는 `/api/vilage-fcst`만 호출되고 특보·강우·해양·태풍 실호출은 없다. 배경 지도/정적 자산 요청은 구분한다.
- 같은 파일·규칙·조작을 재실행하면 수치·등급·모의 영향·자원 결과가 재현된다. 실행 ID 차이는 허용한다.
- 정상/관심/주의/경계/심각 구간의 카드·지도·분석 근거·그래프·브리핑·결재 항목이 같은 실행/시각을 본다.
- 영향 시설 목록 수와 합계, 영향 인구 합계, 자원 보유/가용/요청/투입 수가 서로 맞는다. 가용량 초과·중복 배치를 차단한다.
- 수집상태 오류·지연·누락을 넣어도 위험등급이 자동 상향되지 않는다. 각 화면에서 장애 상태를 확인할 수 있다.
- 보드/상세 창을 열어 둔 채로 시점을 진행하고 승인해도 새로고침 없이 같은 결과가 보인다. 새로고침 후에도 현재 실행이 복원된다.
- 자동 재생을 표시한다면 시간/수치가 실제로 진행된다. 일시정지하면 진행을 멈추며, 복수 창이 같은 시점을 중복 진행하지 않는다.
- 최초 미관측·관측 중간 결측·동일 시각 복수 지점·정상 유지 30분·마지막 관측 이후 예약 처리를 확인한다.
- 승인 기록은 당시 등급·시각을 유지하고, 이후 등급 변동으로 과거 승인 내용이 바뀌지 않는다. 미승인 상태에서 실제 완료 이력을 미리 만들지 않는다.
- 정상 종료는 합의된 조건을 검사한다. 예외 강제 종료 이후 초기화/재업로드로 새 실행을 시작할 수 있고 이전 종료/승인 상태가 남지 않는다.
- 기존 사이트와 스테이징을 동시에 열어 한쪽의 업로드·로그인·초기화가 다른 쪽 상태에 영향을 주지 않는다.
- `npm run build`, `npm run lint`, 하천 재시작/등급/시간/자원 관련 기존 테스트와 필요한 회귀 테스트를 통과한다. 스테이징 빌드/직접 경로 새로고침도 검증한다.
- 스테이징의 일치 검사 결과 어긋남 0건을 확인한다. 기존 `checkConsistency()`가 모의 영향·시계 동기화까지 모두 검사하지는 않으므로 추가한 규칙을 검사 범위에 포함한다.

### 11-1. 스테이징 호스팅·주소·배포 트리거

- **제공자**: Vercel의 별도 프런트엔드 프로젝트를 권장한다. 기존 GitHub Pages 운영 사이트와 origin을 분리할 수 있고, 현재 기상청 프록시도 Vercel에서 운영 중이어서 새 계정 체계를 추가하지 않아도 된다.
- **소스**: 현재 GitHub 저장소 루트를 새 Vercel 프로젝트에 연결한다. Vercel은 한 Git 저장소를 여러 프로젝트에 연결할 수 있다. 기존 `vercel-proxy/kma-weather-proxy` 프로젝트와 프런트엔드 스테이징 프로젝트는 별도 배포 단위다. [Vercel 프로젝트 공식 안내](https://vercel.com/docs/projects)
- **프로젝트명/희망 주소**: `jeju-disaster-platform-staging`, 희망 주소는 `https://jeju-disaster-platform-staging.vercel.app`. 생성 시 이름 사용 가능 여부에 따라 실제 URL을 확정하고 문서·환경 설정에 기록한다. Vercel은 배포에 `vercel.app` URL을 제공한다. [Vercel 도메인 공식 안내](https://vercel.com/docs/domains/working-with-domains/add-a-domain)
- **배포 브랜치**: 장기 브랜치 `staging`을 Vercel 프로젝트의 Production Branch로 지정한다.
- **트리거**: `staging` 브랜치 push 시 스테이징의 고정 주소를 자동 갱신한다. 기능 브랜치 push/PR은 필요할 때 Vercel Preview URL로 확인한다. Vercel Git 연동은 브랜치 push마다 배포하고 Production Branch의 성공 배포를 프로젝트 도메인에 연결한다. [Vercel GitHub 연동 공식 안내](https://vercel.com/docs/git/vercel-for-github)
- **운영 반영**: 검토가 끝난 변경만 `master`에 병합한다. 기존 `master` → GitHub Pages 운영 배포는 유지한다. 스테이징 검토 중인 시나리오와 브라우저 저장 실행은 운영으로 이동시키지 않는다.
- **빌드**: `npm run build:staging` 같은 명시적 명령에서 `vite build --mode staging`을 사용하고, 스테이징 base는 `/`로 둔다. `VITE_APP_ENV=staging`, `VITE_DATA_MODE=simulation`과 동네예보 프록시 공개 URL을 스테이징 환경변수로 설정한다.

GitHub Pages는 저장소당 프로젝트 사이트 하나이므로 현재 저장소 안에서 두 번째 독립 Pages 사이트를 만드는 안은 채택하지 않는다. [GitHub Pages 공식 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

### 11-2. 실행 공유 범위

**1단계는 한 브라우저 프로필에서 독립 시연으로 확정한다.** 시나리오를 올린 사용자가 통합 대시보드·하천 보드·상세 창을 함께 열어 업무 흐름을 검토한다. 같은 origin의 탭/창은 현재 `localStorage`와 `BroadcastChannel` 구조로 동기화한다.

- 다른 PC, 다른 브라우저, 시크릿 창 사이의 실행 공유는 1단계 범위에서 제외한다.
- 새로고침 뒤 현재 실행 복원, 같은 브라우저의 보드/상세 창 즉시 갱신은 필수다.
- 기존 사이트와 스테이징은 저장 키·채널·상세 창 이름에 환경 prefix를 사용해 서로 영향을 주지 않게 한다.
- 화면에 `이 실행은 현재 브라우저에만 저장됩니다`를 표시한다.
- 실행 파일 내보내기/가져오기 또는 서버 저장은 여러 사용자 공동 검토 요구가 실제로 생길 때 2단계로 설계한다. 중앙 저장소 없이 여러 사용자 공유가 된다고 표시하지 않는다.

### 11-3. 하천 모의 시설·구역 및 등급별 영향 규칙

대상지 이름은 확정된 돈내코·쇠소깍을 유지한다. 아래 시설명·인원은 모두 **모의 시연용**이며 실제 시설·거주 인구·기관 보유량을 뜻하지 않는다. 화면 제목과 상세에 `모의`를 표시한다.

고정 모의 시설 카탈로그:

| 지점 | 고정 모의 시설/구역 |
| --- | --- |
| 돈내코 | `D-01 돈내코 모의 하천변 산책구역`, `D-02 돈내코 모의 하상 접근로`, `D-03 돈내코 모의 임시주차구역` |
| 쇠소깍 | `S-01 쇠소깍 모의 하구 산책구역`, `S-02 쇠소깍 모의 하상 접근로`, `S-03 쇠소깍 모의 저지대 대기구역` |

지점별 등급 규칙:

| 현재 운영 등급 | 활성 모의 시설 수 | 모의 영향대상 인원 | 대응 권고 | 지점별 권고 자원 |
| --- | ---: | ---: | --- | --- |
| 정상 | 0 | 0명 | 상시 모니터링 | 없음 |
| 관심 | 1 | 5명 | 현장 확인·연락망 및 자원 가용 여부 점검 | 배치 없음 |
| 주의 | 2 | 15명 | 출입 통제 준비·주민/방문객 안내 검토 | 통제 인력 1, 차단기 1 |
| 경계 | 3 | 30명 | 출입 통제·저지대 대피 준비·경보 승인 검토 | 통제 인력 2, 차단기 1, 출동차 1 |

규칙 적용 원칙:

- 돈내코와 쇠소깍을 각각 계산한 뒤 영향 인원·시설 수를 합산한다. 활성 시설은 위 카탈로그 ID 순서로 선택해 결과가 재현되게 한다.
- `후보 등급`이 아니라 하향 유지시간을 반영한 **현재 운영 등급**에서 영향을 계산한다.
- 위험등급 변화는 영향 및 **권고 자원**만 바꾼다. 실제 자원 요청·승인·도착·복귀는 사용자의 조작으로만 바뀐다.
- 기존 고정 자원 수량(지점별 통제 인력 2, 차단기 1, 출동차 1)을 사용한다. 권고량이 가용량을 넘지 않는지 검사한다.
- 관심 단계의 5명은 실제 피해자가 아니라 점검 대상으로 설정된 모의 영향대상이다. 화면에서 `피해 인원`으로 표현하지 않는다.
- 면적은 공간 모델 없이 임의 제곱미터를 만들지 않는다. `모의 영향 구역 N개`로 표시한다. 대피 경로는 실제 최적경로 대신 시설별 `모의 대피경로 확인/통제` 상태로 둔다.
- 등급별 조치는 `riverStageCriteria.action`을 기준으로 문구를 구성한다. 위 표가 공식 SOP나 실제 기관 배치 기준이라고 설명하지 않는다.
- 실제 배치 수와 권고량이 다르면 오류로 만들지 않고 `권고 N / 배치 M`으로 보여 담당자가 판단하도록 한다.

### 11-4. 수위·강우 모의 시계열의 1단계 포함 여부

**1단계에는 포함하지 않는다.** 하천 위험판정 입력은 기존 합의대로 Q%만 사용한다. Q%에서 수위(m)나 강우(mm)를 역산하면 근거 없는 물리 관계가 생기고, 수위·강우 열을 다시 요구하면 사용자의 수기 입력 부담과 검증 범위가 커진다.

1단계 화면 처리:

- Q% 현재값·변화 그래프·운영 등급·모의 영향·권고 자원·대응 상태를 완성한다.
- 수위·강우·레이더·조위·영상은 `이번 시나리오 입력 범위 밖` 또는 `모의 자료 미제공`으로 표시한다.
- 동네예보는 실시간 참고 패널로 유지하되 Q% 등급이나 모의 영향 계산에 넣지 않는다.
- Q%와 수집상태 엑셀의 센서 표시값을 수위·강우 시계열로 재사용하지 않는다.

2단계에서 그래프 검토가 필요해지면 시나리오 엑셀에 수위·강우를 **선택 열 또는 별도 시트**로 추가해 사용자가 독립적으로 입력한다. 이때도 Q%에서 자동 생성하지 않고, 지점·시각·단위·결측 처리·판정 사용 여부를 명시한다. 2단계 추가 전까지 빈 차트를 임의 곡선으로 채우지 않는다.

3. 위 고정 시설·영향·권고 규칙을 순수 계산 함수로 구현
4. 하천 대시보드·상황 분석·브리핑·지도·자원 화면 동기화
5. 자동 재생·같은 시각 복수 행·종료 조건·강제 종료 후 재실행 회귀 검증

#### Claude 검토 (2026-09-30, §11 대 미커밋 코드 대조 — 문서 작업만, 구현 안 함)

§11의 네 결정안을 현재 미커밋 상태(§9 1~2단계 구현분: `appEnv.ts`·저장 키 분리·실 API 4종 차단·`SourceTag`/`LiveBlock` 표시·`build:staging`)와 코드로 대조했다. 결론: **구조적 충돌은 없고, 이어서 구현 가능하다.** 다만 아래 1건은 실제 배포 전에 반드시 고쳐야 하는 코드 충돌이고, 2건은 §11이 명시했지만 아직 빠진 부분이다.

**충돌 1 — `vite.config.ts`의 base 경로.** 현재 `base: command === 'build' && mode !== 'localhost' ? '/jeju-disaster-platform/' : '/'`라서 `--mode staging` 빌드도 `/jeju-disaster-platform/`을 쓴다. §11-1은 "스테이징 base는 `/`로 둔다"(Vercel은 도메인 루트에 배포)고 명시했다 — 이대로 빌드해 Vercel에 올리면 모든 에셋 경로가 `/jeju-disaster-platform/assets/...`로 잘못 나가 화면이 빈 채로 뜬다. 실제로 로컬에서 `vite preview --outDir dist-staging`으로 이 문제를 직접 재현했다(자산 404 → SPA 폴백이 HTML을 대신 반환 → 빈 화면). 수정은 한 줄: `mode !== 'localhost' && mode !== 'staging'`로 조건을 넓히면 된다(`main.tsx`의 `BrowserRouter basename`은 `import.meta.env.BASE_URL`을 그대로 읽으므로 같이 고쳐진다 — 별도 수정 불필요).

**누락 1 — `VITE_APP_ENV`.** §11-1·§4는 `VITE_APP_ENV=staging`과 `VITE_DATA_MODE=simulation`을 별도 변수로 요구하지만, 현재 코드는 `VITE_DATA_MODE`(`IS_SIMULATION_MODE`) 하나만 읽는다(`.env.staging.example`에도 `VITE_APP_ENV`가 없다). 1차년도 범위에서는 "스테이징이면 항상 모의 데이터"가 1:1이라 변수 하나로도 동작은 같다 — `VITE_APP_ENV`는 지금 아무것도 안 읽어서 추가해도 화면엔 영향이 없다. 실제로 필요해지는 시점은 "스테이징 표시는 하되 실데이터로 시험" 같은 두 값이 갈리는 요구가 생길 때다. 구현 여부는 사용자 판단을 권한다: 지금 `VITE_APP_ENV`도 같이 추가(§11 명세와 완전히 일치, 코드 변화는 미미) vs 보류(불필요한 변수 하나를 안 늘림, YAGNI).

**누락 2 — "이 실행은 현재 브라우저에만 저장됩니다" 표시.** §11-2가 화면에 표시하라고 명시했지만 아직 없다. 현재 헤더 배지(`Header.tsx`)의 툴팁은 "저장 상태는 기존 사이트와 분리됩니다"까지만 말하고, "다른 기기·브라우저와 공유되지 않는다"는 더 구체적인 문장은 없다 — 사용자가 다른 PC에서 같은 스테이징 주소로 들어가면 이어진다고 오해할 여지가 있다. `RiverScenarioPage.tsx`(업로드·실행 화면)에 한 줄 추가하는 것을 권한다.

**충돌 없음으로 확인한 부분**: §11-3의 고정 자원 수량(지점별 통제 인력 2·차단기 1·출동차 1)은 `mockRiverResources.ts`의 실제 `capacity` 값과 정확히 일치한다(Codex가 코드를 보고 역산한 숫자로 보인다). `riverStageCriteria`에 `action` 필드가 이미 있어 §11-3이 요구하는 "등급별 조치 문구는 `riverStageCriteria.action` 기준" 계획도 별도 데이터 추가 없이 바로 계산 함수로 옮길 수 있다. §11-4(수위·강우 시계열 1단계 제외)는 현재 코드가 이미 그 상태(Q%만 판정 입력)라 변경이 필요 없다. §11-2(단일 브라우저 시연)도 현재 `localStorage`/`BroadcastChannel` 구조와 그대로 맞는다.

**아직 없는 것(§11-3·§11-4의 본 내용, §9 3~4단계)**: 돈내코·쇠소깍 고정 모의 시설 카탈로그(D-01~03·S-01~03), 등급별 영향 인원·시설 수·권고 자원 계산 함수, 그 값을 상황 분석·대시보드·브리핑·지도에 동기화하는 작업은 전부 미구현이다 — §11 문서가 방금 설계를 확정한 것이지 코드가 아니므로 당연한 상태이며, 별도 착수 지시가 있어야 진행한다.

**외부 상태(호스팅) 관련**: Vercel 프로젝트 생성·`staging` 브랜치 생성·환경변수 등록·GitHub 연동은 전부 미착수(코드 변경이 아니라 외부 계정 조작이라 별도 실행 요청 필요, §11-5와 동일 결론).
