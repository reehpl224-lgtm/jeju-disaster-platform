# DB 인계·관리 안내 (처음 보는 분용)

개발을 잘 모르는 분이 읽고 개발팀에 넘길 수 있게 쉬운 말로 적었습니다. 기술 상세는 [README.md](./README.md)에 있습니다.

## 1. DB가 깃(Git)에 있나요?

**아니요. 깃에는 DB 자체가 아니라 DB의 설계도만 있습니다.**

- **DB** = 실제 데이터가 쌓이는 곳입니다. 서버 프로그램이 돌아가는 컴퓨터(또는 클라우드)에 따로 만들어집니다. 깃에 올리지 않습니다. 올리면 개인정보·운영 데이터가 공개 저장소에 노출됩니다. 이 저장소는 공개입니다.
- **설계도** = "어떤 표를 만들고, 각 표에 어떤 칸이 있는지"를 적은 글 파일입니다. 깃에 있고 지금은 `docs/db/schema.sql`입니다.
- 비유: 깃에는 **건물 설계도**가 있고, **건물(DB)** 은 아직 짓지 않았습니다. 개발팀이 설계도대로 건물을 짓고 데이터를 채웁니다.

지금 사이트는 DB가 없어서, 입력한 내용이 **사용자 브라우저 안**에만 저장됩니다. 다른 PC에서는 보이지 않고, 브라우저 데이터를 지우면 사라집니다.

## 2. 파일 지도 (`docs/db/`)

| 파일 | 한 줄 설명 | 누가 보나 |
|---|---|---|
| **START-HERE.md** (이 문서) | 전체 안내·체크리스트·관리 방법 | 기획·관리자 |
| [README.md](./README.md) | 어떤 값이 어느 표로 가는지, API 후보, 주의점 | 개발팀 |
| [schema.sql](./schema.sql) | 표 설계도 40개(표준 SQL) | 개발팀(DB를 만들 때 실행) |
| [seed.sql](./seed.sql) | 처음에 넣을 코드값(서비스 9종, 위험 4단계, 역할 4종) | 개발팀 |
| [seed-reference.sql](./seed-reference.sql) | 위험 단계 기준·메시지 유형 등(코드에서 자동 생성) | 개발팀 |

코드 쪽 연결 지점은 `src/data/persistence.ts` 한 파일입니다. 지금은 브라우저에 저장하고, 개발팀이 서버 저장으로 바꿀 때 이 파일만 교체하면 됩니다.

## 3. 개발팀에 넘길 때

**전달 문구 예시** (그대로 보내셔도 됩니다)

> 제주 재난 대응 플랫폼 프로토타입의 DB 인계 자료입니다. 저장소의 `docs/db/START-HERE.md`부터 읽어 주세요.
> 현재는 서버·DB 없이 브라우저 저장으로 동작합니다. `schema.sql`(표 40개, 표준 SQL)을 기준으로 DB를 만들고, `seed.sql`과 `seed-reference.sql`을 넣은 뒤, `src/data/persistence.ts`를 서버 연동으로 교체하면 됩니다.
> 인증은 목업이라 실제 로그인과 서버 쪽 권한 검사가 필요합니다. 외부 연계 값(도청·서귀포 CCTV·실증사)은 10월 중순 자료를 받은 뒤 `observation` 등의 열을 확정해야 합니다.

**개발팀이 하는 일 순서**
1. DB 서버를 만든다(종류는 개발팀 결정. PostgreSQL을 가정해 작성했고 표준 SQL 위주).
2. `schema.sql` → `seed.sql` → `seed-reference.sql` 순서로 실행한다.
3. 서버(API)를 만든다. 후보 목록은 README 3번에 있다. 상태 규칙(지시 → 전달 → 수행 중 → 완료 등)과 승인 규칙을 서버에서도 검사한다.
4. 실제 인증을 붙이고, 서버에서 권한을 다시 검사한다.
5. `persistence.ts`를 서버 연동으로 교체하고 화면을 확인한다.
6. 연계 자료가 오면 `observation` 등을 실제 필드에 맞춘다.

**넘기기 전에 정해 두면 좋은 것** (개발팀이 물어볼 내용)
- [ ] 사용할 DB 종류와 설치 위치(클라우드 / 도청 서버)
- [ ] 로그인 방식(도청 계정 연동 여부)
- [ ] 이용 이력·관측값을 얼마나 오래 보관할지
- [ ] 연락처(이름·전화번호)를 실제 값으로 넣을지, 누가 볼 수 있게 할지
- [ ] 운영 환경 접속·백업을 누가 맡을지(운영 담당자)

## 4. DB는 어떻게 관리하나요?

DB 관리는 보통 **개발·운영 담당자**가 합니다. 기획자는 아래 항목이 갖춰졌는지 확인하고 결정할 일을 정해 주시면 됩니다.

**① 환경을 나눕니다** — 개발용, 스테이징(시연), 운영, 이렇게 DB를 따로 둡니다. 운영 데이터를 스테이징에 복사하지 않습니다(개인정보). 스테이징에는 "샘플" 표시가 있는 임의 값만 넣습니다.

**② 접속 정보는 글에 쓰지 않습니다** — DB 주소·아이디·비밀번호는 깃, 문서, 메신저에 적지 않습니다. 서버의 환경 변수(예: Vercel 환경 변수)나 비밀 관리 도구에만 둡니다. 지금도 API 키를 같은 방식으로 관리하고 있습니다.

**③ 백업이 가장 중요합니다**
- 매일 자동 백업을 겁니다. 백업 보관 기간을 정합니다(예: 30일).
- 백업이 있어도 **복구가 되는지 한 번은 직접 해 봅니다.** 복구 해 보지 않은 백업은 없는 것과 같습니다.
- 표 구조를 바꾸기 전에는 반드시 따로 백업합니다.

**④ 계정 권한을 나눕니다** — 앱이 쓰는 계정은 읽기·쓰기만 되고 표 삭제·구조 변경은 못 하게 합니다. 구조를 바꿀 수 있는 관리자 계정은 소수만 갖고, 퇴사·인사이동 때 바로 회수합니다.

**⑤ 표 구조는 "변경 파일"로 바꿉니다** — `schema.sql`을 직접 고쳐서 운영 DB에 다시 실행하면 데이터가 날아갑니다. 구조를 바꿀 때는 `001_add_column.sql`처럼 번호를 붙인 변경 파일을 따로 만들어 쌓고(이를 마이그레이션이라고 합니다), 개발 → 스테이징 → 운영 순서로 적용합니다. 설계도(`schema.sql`)는 최신 모양을 보여 주는 기준 문서로 같이 갱신합니다.

**⑥ 기준값을 바꿀 때** — 위험 단계 기준 같은 값은 코드에도 있고 DB 시드에도 있습니다. 코드에서 고쳤다면 `npm run db:seed`로 시드 파일을 다시 만든 뒤 DB에도 반영합니다. 화면 판정이 DB 값을 읽게 바뀌기 전까지는 코드의 값이 우선입니다.

**⑦ 개인정보와 보관 기간** — 연락처(이름·전화번호)와 이용 이력은 개인정보에 해당할 수 있습니다. 누가 볼 수 있는지, 얼마나 보관하는지, 기간이 지나면 어떻게 지우는지를 정해 문서로 남깁니다.

**⑧ 정기 점검** — 디스크 용량(관측값은 계속 쌓입니다), 느린 조회, 백업 성공 여부를 주기적으로 확인합니다.

## 5. 지금 이 프로젝트의 DB 상태 한눈에

| 항목 | 상태 |
|---|---|
| 실제 DB | 없음(개발팀이 구축) |
| 표 설계도 | 있음 — 40개, 빈 DB에서 한 번에 실행되는 것까지만 확인(PostgreSQL 실행은 미확인) |
| 처음 넣을 값 | 있음 — 코드값 + 위험 기준 등 |
| 코드의 저장 출입구 | 있음 — `persistence.ts` (지금은 브라우저 저장) |
| 인증·서버 | 없음 — 목업 |
| 외부 연계 열 확정 | 10월 중순 자료 수령 후 |
