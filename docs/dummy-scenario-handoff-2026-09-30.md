# 더미데이터 기반 재난대응 시나리오 검토 인계

작성: Codex / 2026-09-30 (Asia/Seoul)

상태: 사용자 요청에 따른 Claude 검토용 인계. 이 문서 작성은 앱 기능 구현, 데이터 주입, 배포를 의미하지 않는다.
검토 기준: 같은 날 로컬 저장소 코드. 이후 변경되었을 수 있으므로 Claude는 작업 시 최신 코드를 다시 확인한다.

## 1. 사용자가 직접 설명한 목적

> 나는 각 서비스 별로 수치들이 변화하는걸 보려고 해.
> 그 변화의 값에 따라 '관심, 주의, 경계, 심각'의 값을 체크하고 그걸로 재난대응을 진행하는 프로세스를 해보고 싶어.
> 그렇기에 각 서비스의 변동하는 데이터는 내가 더미데이터로 넣고 싶어.
> 그 외의 데이터는 임의로 만들어 넣었으면 해.(재난인원 배치라던가..)
> 그런부분을 체크, 확인해서 안내해줘.

이후 사용자 요청: 위 검토 내용을 Claude가 확인할 수 있도록 처리.

핵심은 단순한 데이터 수집 목록 채우기가 아니다. 사용자가 시간별 위험 판단 입력값을 통제하고, 시스템이 그 값에 따른 등급과 대응 과정을 일관되게 보여주는 시험이다.
기존 `수집데이터` 엑셀만 수정하면 이 목표가 이미 달성되는 것으로 설명하지 않는다.

## 2. 입력 데이터와 보조 데이터 분리안

아래는 Codex의 설계 제안이며 세부 열·형식·구현 순서는 아직 사용자 확정 전이다.

| 구분 | 사용자 입력 또는 선택 | 자동 준비·계산 |
| --- | --- | --- |
| 위험 판단 입력 | 서비스, 대상지, 관측시각, 지표별 수치, 판정에 영향을 주는 사건 | 입력 검증, 단위 확인, 시계열 정렬 |
| 위험등급 | 등급 자체를 수동으로 강제 입력하지 않는 방안 권장 | 기준에 따른 판정과 근거, 이전 등급 대비 변화 |
| 고정 기본정보 | 다른 항목을 쓰거나 새 항목을 추가할 때만 수정 | 기존 확정 대상지·센서 ID·항목명·단위 재사용 |
| 가상 대응 자원 | 필요하면 규모·조건 조정 | 가상 담당자·기관 역할·가용 인력·장비·차량 |
| 배치·경보 초안 | 사용자가 확인·승인·수정 | 상황·등급에 맞는 배치안, 경보 문안, 점검 목록 |
| 외부 응답 모의 | 성공·실패·지연 조건 선택 가능 | 접수·출동·도착 등 모의 응답 |
| 대응 이력·보고 | 사용자 판단과 조치 | 실제 시험 조작에서 발생한 이력과 종료 보고 초안 |

보조 데이터의 원칙:

- 지리적 대상지와 확정된 계획·시설 규모는 `AGENTS.md`의 Ground Truth를 따르고 임의 변경하지 않는다.
- 인력·장비는 가상 자원임을 표시하고, 같은 시험을 다시 실행해도 재현할 수 있게 고정된 세트 또는 저장된 생성값을 쓴다.
- 가용 인원을 넘거나 같은 인력·장비가 여러 현장에 중복 배치되지 않도록 한다.
- 담당자 연락처는 실제 발송 가능한 임의 번호를 만들어 쓰지 않는다. 테스트 식별자·비발송용 표기를 사용한다.
- 승인·출동·완료 이력을 미리 완료 상태로 생성하지 않는다. 사용자가 대응을 진행해야 이력이 쌓여야 한다.
- 연안의 인명 고립·월파처럼 등급을 바꾸는 사건은 단순 보조 데이터가 아니다. 사용자 선택 또는 명시적인 고정 조건으로 관리하며 숨겨진 무작위 입력으로 넣지 않는다.
- 수집상태(정상·지연·오류·누락), 위험등급, 업무 진행상태는 서로 별개의 값이다.

## 3. 서비스별 변동 입력 후보와 현재 격차

| 서비스 | 입력 후보 | 코드 확인 결과 및 확인할 사항 |
| --- | --- | --- |
| 하천범람 | 시각, 돈내코/쇠소깍, 수위, 유량 또는 계획홍수량 대비 비율 | `mockRiver.ts`의 `riverStageCriteria`는 계획홍수량 대비 비율 기준. 수위(m)를 이 비율로 임의 환산하지 말 것. 지점별 관계가 없으면 시험용 비율을 명시적으로 입력하는 방안 검토 |
| 저염분·고수온 | 시각, 한경 금등/한경 용수/대정 일과, 염분, 수온 | `marineAlertThresholds.ts` 판정 함수 재사용. 지속일수 및 복합 조건 반영. 이력으로 지속시간을 계산하거나 초기 지속기간을 명시적으로 입력하는 방안 검토 |
| 연안 안전 | 시각, 함덕/협재, 파고, 풍속, 조위 상태, 영상 사건 종류 | `coastAlertThresholds.ts` 판정 함수 재사용. 현재 조위 입력은 숫자가 아니라 `TideState`이므로 수치 조위를 쓸 경우 지점별 상태 변환 기준이 추가로 필요 |
| 호우 | 시각, 지점, 강우량, 기간별 누적강우량, 침수심 등 | 측정값 표시와 5단계 판정·대응의 통합 연결 필요. 어떤 관측 지표가 어느 등급을 만드는지 기준 검토 필요 |
| 폭염 | 시각, 지역, 체감온도, 지속시간 등 | 현재 특보 참고 기준과 서비스 위기단계의 대응 관계 검토 필요. 기상특보와 재난대응 5단계를 동일시하지 말 것 |
| 태풍 | 시각, 위치·접근거리, 풍속, 예상 도달시각 등 | `TyphoonHomePage.tsx`는 특보 상태→등급 매핑 사용. 수치 기반 시험 규칙 및 심각 단계 조건 검토 필요. 자체 AI 예측처럼 표기하지 말 것 |

공통 위험등급은 기존 `safe(정상) < caution(관심) < warning(주의) < alert(경계) < danger(심각)` 유지.
사용자가 모든 서비스를 언급했으므로 호우·폭염·태풍을 최종 범위에서 임의 제외하지 않는다.
하천·저염분·연안 우선 구현 후 나머지를 확장하는 순서는 Codex의 제안일 뿐, 사용자 확정 사항이 아니다.

## 4. 현재 코드에서 확인한 제약과 검토 근거

- `src/data/dummyWorkbook.ts`
  - 기존 엑셀은 수집 항목 목록·수집상태를 표시하는 용도.
  - 동일 서비스 안에서 `항목ID` 중복을 막으므로 같은 센서의 여러 시각을 그대로 추가하면 거절된다.
  - 호우 `status`를 `safe`로 유지하며 수집상태만 `collectionStatus`에 넣는다. 통신 오류가 재난 심각으로 바뀌지 않도록 한 의도적인 분리다.
  - 하천 상황 수치·연안 위험 사건·종료 이력 전체를 연결하는 업로더가 아니다.
  - 입력된 서비스 목록은 교체하고 파일에 없는 서비스는 유지한다. 이 동작을 새 기능에서 무심코 깨지 않도록 한다.
- `src/data/scenarios.ts`
  - 현재 기본 빈 시나리오만 등록되어 있다. 앱 시작 시 한 번 데이터를 적용하는 구조이며 시간별 재생 기능은 없다.
- `src/data/scenarioClock.ts`, `src/main.tsx`
  - 기존 시나리오 시각 이동과 사용자 입력 관측시각을 구분한다. 사용자 시계열을 현재 시각으로 몰래 이동시키지 않는다.
- `src/pages/aqua/AquaResponsePage.tsx`, `AquaAlertPage.tsx`, `src/pages/coast/CoastAlertPage.tsx`, `CoastDispatchPage.tsx`, `src/pages/river/RiverAlertPage.tsx`
  - 일부 동작이 페이지 로컬 `useState`에 머문다. 화면 간 연결·새로고침·보드와 상세 창 동기화에 대한 공통 상태 설계 필요.
- `src/pages/river/RiverDispatchPage.tsx`
  - 기관별 출동 표가 고정 빈 상태 문구를 표시한다. 데이터를 채우는 것만으로 실제 출동 진행 표가 구현되는 것은 아니다.
- `src/types/flow.ts`
  - 감지→확인→판단→경보→대응→종료 단계 타입은 있다. 위험등급과 업무 진행단계는 합치지 않는다.
- `src/data/consistency.ts`, `src/pages/domain/leaderBriefs.ts`, `src/pages/domain/domainConfigs.tsx`
  - 카드·지도·브리핑·보드·상세 화면이 동일한 시점과 사건 데이터를 읽도록 연결 및 정합성 검사 필요.
- `src/data/mockContacts.ts`
  - 기존 가상 담당자 안내가 있다. 중복된 인력 기준정보를 새로 만들기 전에 재사용 가능성을 검토한다.

### 판정 기준의 불일치·미구현 사항

1. 염분 24.0psu: 현재 `classifySalinity()`는 24.0을 경계로 분류하고 `AGENTS.md`도 심각을 `<24.0`으로 적는다. 하지만 함수 파일의 일부 주석은 `24.0 이하`로 기재되어 있다. 이전 Codex 답변의 '코드·주석 차이'는 이 불일치를 뜻한다. 자동으로 코드를 `<=24.0`으로 바꾸라는 지시가 아니다. 확정 문서·사용자 결정과 대조하고 설명을 정리한다.
2. 연안: '낮은 지표가 30분 유지된 뒤 한 단계씩 하향'은 주석·안내에 있으나 `classifyCoastRisk()` 자체는 현재 입력만 계산한다. 과거 시점과 현재 적용 등급을 가진 별도 시간 로직이 필요하다.
3. 하천 관심 구간의 빈 구간 보완과 연안 지표 결합은 기존 사용자 요청에 따른 임시 규칙이 포함된다. 공식 운영 기준으로 단정하지 않는다.
4. 결측·통신 오류를 위험 수치 0 또는 정상으로 자동 치환하지 않는다. 마지막 유효값의 시각·품질과 판정 불가 여부를 별도로 표현하는 방안을 검토한다.

## 5. 권장 사용자 시험 흐름 (설계 제안)

1. 시간별 시나리오 엑셀 작성: 서비스·대상지·시각·각 지표 값. 기존 수집상태 엑셀과 목적을 구분한다.
2. 업로드 검증: 지점, 단위, 숫자 범위, 시각 형식, 중복 시점, 시간순서, 필요한 기간 이력 검사.
3. 적용 전 미리보기: 수치 그래프, 판정 결과·근거, 적용한 기준·보조 조건.
4. `다음 시점`으로 한 단계씩 진행. 자동 재생·일시정지·속도 선택은 후속 선택지.
5. 수치에 따른 등급 판정 후 사용자가 상황 확인·경보 승인·배치 확정·출동 요청·조치를 수행.
6. 정해진 조건으로 모의 응답을 반환하고 사건 이력에 기록.
7. 하향·해제 조건과 미완료 조치를 확인하여 종료 보고 생성.

추가 설계 주의:

- 동일 센서의 다른 시각은 허용하고, 동일 시각 중복의 처리 원칙을 명시한다. 예: `시나리오ID+서비스+지점/센서ID+관측시각` 키.
- 미래 행은 미리보기에는 보여줄 수 있지만 현재 시험시점의 등급·지속시간·대응에는 유입되지 않아야 한다.
- 등급 상향 계산과 경보 발령 승인은 분리한다. 관심 단계라고 모든 서비스에서 대외 경보를 자동 발송하지 않는다.
- 재시작·되감기 시 기존 대응 이력의 초기화 또는 별도 실행 분리 규칙이 필요하다. 이를 사용자에게 알리지 않고 기록을 지우지 않는다.
- 수치·등급·대응을 하나의 공통 사건 상태에서 파생시키고 화면별 하드코딩을 늘리지 않는다.
- 실제 API는 유지한다. 시험 모드의 판정 입력은 시나리오로 명확히 지정하고 실제 API는 별도 참고로 표시한다.
- 문자·방송·기관 출동 요청은 모두 모의 처리. 실제 발송·외부 기관 호출·물리 장비 제어를 하지 않는다.
- 기존 `*` 더미 표식, 실시간/스냅샷 태그를 유지하고 시험시각을 표시한다.

## 6. Claude에게 요청하는 검토 결과

지금은 아래를 검토해 사용자에게 설명하는 단계다. 이 인계 문서만으로 대규모 구현을 시작하지 않는다.

1. 사용자 직접 입력 열과 시스템 자동 준비 항목을 서비스별로 확정 가능한 것/추가 확인할 것으로 나누기.
2. 기존 코드 재사용 범위와 새로 연결해야 할 범위를 제시하기.
3. 등급 판정 기준, 경계값, 지속시간, 하향·종료 조건의 미확정 사항을 정리하기.
4. 수집상태 엑셀을 유지하면서 별도 시계열 시나리오 엑셀을 추가할지, 호환 가능한 확장으로 갈지 제안하기.
5. 보드·상세 창·페이지 이동·새로고침 간 대응 상태를 유지할 방법을 최소 범위로 제안하기.
6. 가상 인력·장비 배치와 사용자 승인 동작의 범위를 제안하기.
7. 구현 순서와 변경 예정 파일을 사용자에게 먼저 안내하기.

## 7. 구현 승인 후 적용할 검증 제안

- 각 서비스에서 정상→관심→주의→경계→심각과 하향·종료를 시간순으로 시험.
- 임계값 직전·일치·직후, 지속시간 경계, 복합조건, 결측·지연·오류를 검사.
- 수집 오류만 변경했을 때 재난등급이 임의 상승하지 않는지 검사.
