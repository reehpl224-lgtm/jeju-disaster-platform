## 1. 공통 기반 — 테스트베드 서버에 들어가야 할 것

레거시 데이터 문서(3항)의 원칙대로, 모든 판정은 **"자동 발령"이 아니라 "조기 알람 + 담당자 최종
승인(Human-in-the-loop)"** 구조로 설계합니다.

| 구성 | 역할 | 비고 |
|---|---|---|
| 수집 스케줄러 | 기상청 AWS(1분~10분)·sea_obs·단기예보·특보·태풍·KHOA API를 주기 호출 | 기존 Vercel 프록시(`kma-weather-proxy`) 재사용 가능 |
| 시계열 DB | 수집값 누적 — 추세 분석·오경보 검증·향후 모델 학습의 기반 | 지금은 어디에도 쌓이지 않음 |
| 판정 엔진 | 서비스별 규칙·임계값 실행 → 단계 산출 | 이미 코드에 있음: `classifyCoastRisk`, `classifyMarineRisk`, 하천 단계표 |
| 알림·승인 | 판정 결과를 담당자에게 알리고, 승인 시 대외 발송 요청 | 담당자 연락처는 문서상 업무 목적 등록 가능 |
| 이력 로그 | 판정·승인·발송 이력 저장(종료 보고서 자동 작성 근거) | 현재 화면의 이력은 더미 |

> 판정 함수들이 이미 프론트엔드 코드(`src/data/*Thresholds.ts`)에 있으므로, 서버로 옮길 때
> 같은 로직을 재사용하면 화면 판정과 서버 판정이 어긋나지 않습니다.

## 2. 서비스별 상세

### 2.1 연안 안전관리 — ✅ 예측 가능

**쓸 수 있는 데이터(①, 실제 필드)**: 기상청 sea_obs — 협재(정확 일치)·김녕(함덕 인근)의
유의파고(`waveHeightM`)·풍속(`windSpeedMs`)·수온, 실시간 · 기상청 풍랑/해일 특보 · 단기예보.

**만들 수 있는 것**
1. **실시간 위험단계 판정** — sea_obs 협재·김녕 값을 이미 있는 `classifyCoastRisk()`(파고·풍속
   결합 규칙)에 그대로 넣으면 됩니다. 지금은 이 함수가 외해 KHOA 부이 예시에만 적용돼 있는데,
   sea_obs는 해수욕장 인근 지점이라 훨씬 적합합니다. **가장 빨리 만들 수 있는 항목**입니다.
2. **3일 위험단계 예보** — 단기예보 API에는 파고(`WAV`)·풍속(`WSD`) 항목이 있는데 앱은 아직
   WSD만 파싱합니다. WAV를 추가로 받아 같은 규칙에 넣으면 시간별 예상 위험단계가 나옵니다.
   단, WAV는 해상 격자에서만 제공되므로 협재·함덕 앞바다의 해상 격자 좌표로 조회해야 합니다.

**한계**: 조위는 현지 관측이 없어 계속 "평시 가정"(모슬포는 20~53km 떨어져 참고용).
이안류·익수 같은 사람 대상 위험은 AI CCTV(③ 실증사) 영역입니다 — 과거 사고 영상(④)이 없어
자체 학습은 불가합니다.

**대응**: 단계 상승 시 담당자 알림 → 현장 전광판 문구·안내 방송 초안 → 승인. 실제 방송·해경
자동 연계는 함덕 종합상황실 기존 CCTV·방송스피커(② 협의 완료) 연계가 필요합니다.

### 2.2 호우 — ✅ 예측 가능

**쓸 수 있는 데이터(①)**: 기상청 AWS 매분자료 — 15분·60분·12시간·일 누적 강우
(`rain15mMm`·`rain60mMm`·`rain12hMm`·`rainDayMm`), 풍속·풍향, 실시간 · 호우특보 · 단기예보.

**만들 수 있는 것**
1. **특보 기준 도달 조기경보** — 기상청 호우특보 기준(주의보: 3시간 60mm 또는 12시간 110mm,
   경보: 3시간 90mm 또는 12시간 180mm)에 대해, 실측 누적 + 최근 강우 강도로 "기준 도달 예상
   시각"을 외삽합니다. 규칙 기반이라 설명 가능하고 오경보 원인 추적도 쉽습니다.
2. **예보 대비 실측 초과 감지** — 단기예보의 1시간 강수량(`PCP`, 현재 미파싱)과 AWS 60분 실측을
   비교해 "예보보다 강하게 오는 돌발 강우"를 잡습니다. 지금 대시보드의 "AI 조기경고"
   (`heavyRainAiForecast`)가 바로 이 개념인데 값이 더미라, 실데이터로 바꾸는 작업입니다.
   면담에서 "기상청 예측을 벗어나는 돌발 폭우가 가장 대응이 어렵다"는 지적과 정확히 맞습니다.

**한계**: AWS 참고지점이 서귀포·제주남원 2곳뿐입니다. 제주시(한천 등) 지점 추가가 필요하고,
지점번호 조회가 이 작업 환경의 네트워크 정책(`kma.go.kr` 차단)으로 보류돼 있습니다.
침수센서·우량계 원본은 ② 레거시(섬엔지니어링 API 협의) 연계 전까지 더미입니다.

**대응**: 담당자 알림 → 재해문자전광판·자동음성 송출 초안 → 승인. 실제 송출은 ② 강우량 연동 자동
경보 발령시스템 연계 대상입니다.

### 2.3 폭염 — ✅ 예측 가능

**쓸 수 있는 데이터(①)**: 단기예보 시간별 기온(`TMP`)·습도(`REH`), 3일 · 폭염·열대야 특보.

**만들 수 있는 것**
1. **폭염특보 기준 도달일 예측** — 기상청 여름철 체감온도 산식(기온·상대습도 기반)으로 단기예보
   값을 시간별 체감온도로 바꾸고, 특보 기준(주의보: 일최고 체감 33℃ 이상 2일 이상, 경보: 35℃)
   도달 여부·날짜를 미리 표시합니다. 특보 발표 전에 무더위쉼터 개방 준비를 시작할 근거가 됩니다.

**한계·확인 필요**: 무더위쉼터 공식 목록(④)은 공공데이터포털에 행정안전부 무더위쉼터 데이터가
공개돼 있는지 확인해볼 가치가 있습니다 — 있다면 ④에서 ①로 바로 옮길 수 있습니다.
열섬 정밀지도는 대체 수단이 없습니다.

**대응**: 취약계층 안내 문자·쉼터 개방 체크리스트 초안 → 승인.

### 2.4 태풍 — ✅ 계산형 가능 (AI 예측 아님)

**쓸 수 있는 데이터(①)**: 기상청 태풍 API — 분석·**예측 위치**(`ft="1"`), 진행 방향·속도,
중심기압, 최대풍속, **강풍반경 15m/s·25m/s**(`rad15Km`·`rad25Km`), 실시간 · 태풍특보.

**만들 수 있는 것**
1. **제주 영향 시각 산출** — 예측 경로의 각 지점과 제주 사이 거리에서 강풍반경을 빼면 "초속
   15m 강풍권·25m 폭풍권이 제주에 닿는 예상 시각"이 나옵니다. 지금 경로 분석 화면
   (`typhoonForecastTrack`)이 더미인데, 이 실데이터로 바꿀 수 있습니다.
2. **대비 발령 자동 개시** — 영향 예상 시각 N시간 전에 대비 체크리스트(e-SOP)를 자동으로
   열어 담당자에게 알립니다.

**한계**: 경로 자체의 예측은 기상청 몫이며 자체 AI는 구조상 불필요·불가합니다(레거시 문서 2.2항).

### 2.5 저염분 고수온 — ⚠️ 부분 가능

**쓸 수 있는 데이터(①)**: KHOA 해양관측부이·조위관측소 4곳 수온·염분(2곳은 유속·유향).
API 자체는 실시간이지만 **앱은 2026-09-09 스냅샷을 고정 표시** 중입니다.

**만들 수 있는 것**
1. **실시간 단계 판정** — KHOA API를 서버에서 주기 수집해 이미 있는 `classifyMarineRisk()`
   (TP-P22_002 기준 5단계)에 넣습니다.
2. **염분 하강 추세 조기경보** — 수집값이 쌓이면 "하루 몇 psu씩 떨어지는지"로 관심 기준
   (30.0psu) 도달 예상일을 외삽할 수 있습니다. 단, 관측점이 양식장 해역(한경 용수)과 13~155km
   떨어져 있어 국지 예측에는 부족합니다.

**정식 예측(수일 전 확산 예측)**: 실증사(③ ROMS·NEMO + AI, 위성, 양쯔강 유출량)의 몫입니다.
상세 요청안은 `docs/khoa-ai-prediction-requests.md` 참고.

**대응**: 관심 단계 점검·예찰 체크리스트는 이미 화면에 있음 → 서버 판정과 연결. 어가 다채널
자동경보는 승인권자 미확정(④)이라 보류.

### 2.6 하천범람 — ❌ 현재 불가 (선행 조건 2개)

**쓸 수 있는 데이터(①)**: AWS 우량(서귀포·제주남원 참고지점) · 단기예보 · 호우특보 ·
모슬포 조위(정적 스냅샷, 25km 떨어짐).

**왜 지금 불가한가**: 범람 예측의 핵심인 **하천 수위 실측이 없습니다**(④, 화면 값은 더미).
강우만으로는 "위험할 수 있음" 수준의 대리지표만 가능합니다.

**가능해지려면**
1. **② 하천모니터링시스템 수위 연계** — 레거시 문서상 수위 데이터가 DB에 이미 누적 중입니다.
   섬엔지니어링과 API 협의가 되면 실시간값 + 과거 이력을 함께 얻습니다.
2. **수위–유량 관계곡선 확보** — 하천 단계표(TP-P22_002)는 "계획홍수량 대비 %"(유량) 기준인데
   센서는 수위를 잽니다. 효돈천의 관계곡선(rating curve)이 있어야 수위를 단계로 환산할 수
   있습니다. **실증사(소다시스템)나 도에 보유 여부를 확인**해야 합니다.

두 조건이 갖춰지면: 수위 추이 조기경보(대시보드에 이미 화면 있음, `riverWaterLevelAiForecast`)를
실데이터로 가동하고, 1시간 선행 범람예측(③ 실증사, 정확도 85%↑)을 받아 붙이는 순서가 됩니다.
ETRI 효돈천 수문데이터(2011~2023, 실증사 보유)가 학습·검증 데이터로 쓰일 수 있습니다.

## 3. 권장 구축 순서

| 단계 | 내용 | 필요한 것 | 규모 |
|---|---|---|---|
| **1** | 테스트베드 서버 — 수집 스케줄러 + 시계열 DB + 알림 | 서버 1대(또는 Vercel 크론 + DB) | 공통 기반 |
| **2** | 연안 실시간 위험단계(sea_obs → `classifyCoastRisk`) | 1단계만 있으면 됨 | 소 |
| **3** | 호우 특보 기준 도달 조기경보(AWS + PCP) | 1단계 + 단기예보 PCP 파싱 | 소~중 |
| **4** | 폭염 특보 도달일 예측(체감온도) · 태풍 영향 시각 산출 | 1단계 | 소 |
| **5** | 아쿠아 KHOA 주기 수집 → 단계 판정 실시간화·추세 외삽 | 1단계 + 수집 누적 기간 | 중 |
| **6** | 하천 수위 연계 → 수위 추이 조기경보 가동 | ② 섬엔지니어링 API 협의 + 관계곡선 | 대(협의 필요) |
| **7** | 실증사 예측모델 연결(하천 1시간·아쿠아 수일·연안 AI CCTV) | ③ 실증사 API | 실증사 일정 따름 |

2~4단계는 **지금 연동된 공공 API만으로** 가능하고, 이미 코드에 있는 판정 규칙을 재사용하므로
