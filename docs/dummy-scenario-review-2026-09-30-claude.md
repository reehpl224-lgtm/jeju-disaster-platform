## 0. 기술적 사실 확인 (코드 직접 대조)

인계 문서의 주장을 하나씩 코드로 확인했다. 전부 정확했다.

- `classifySalinity()`(`marineAlertThresholds.ts`)의 `>=24.0psu → 경계`, `<24.0psu → 심각` 경계는
  `AGENTS.md`와 정확히 일치한다. 인계 문서가 짚은 "주석 불일치"는 원본 엑셀 문구("24.0 이하")와
  실제 구현 경계값의 표현 차이일 뿐 — 코드·`AGENTS.md`는 이미 서로 맞다. 사소하므로 우선순위 낮음.
- `classifyCoastRisk()`(`coastAlertThresholds.ts`)는 정말 순수 함수다. 이전 상태·경과 시간을
  전혀 기억하지 않는다. "30분 유지 후 하향" 규칙은 주석·`COAST_COMBINE_RULES` 문구에만 있고
  실제로 동작하는 코드는 없다.
- `RiverDispatchPage.tsx`의 "기관별 출동 요청 현황" 표는 데이터를 전혀 참조하지 않는 완전한
  하드코딩 JSX다. 무엇을 넣어도 "출동 요청 이력 없음"만 나온다.
- `dummyWorkbook.ts`는 서비스+항목ID로 중복을 막아서, 같은 센서의 여러 시각(시계열)을 못 넣는다.
- `scenarios.ts`는 등록된 시나리오가 `default`(빈 상태) 하나뿐이고, 앱 시작 시 한 번 덮어쓰는
  구조라 "다음 시점으로 진행" 같은 재생 개념이 없다.
- 하천은 코스트·아쿠아와 달리 `classifyRiverRisk()` 같은 **판정 함수가 없다.** `riverStageCriteria`는
  문자열 범위("20% 이상 ~ 50% 미만")로 적힌 표일 뿐, 숫자를 넣으면 등급을 돌려주는 함수가 아니다.
  숫자 기반 시나리오를 만들려면 이 함수를 먼저 만들어야 한다.
- 하천의 "30분 유지 후 하향/종료" 규칙은 지금 코드에 없다. 2026-09-22 리셋 이전 히스토리
  (git log, 지금은 지워짐)에 "수위 대피 기준 이하로 30분 이상 유지" 같은 지난 사례 문구가 있었을
  뿐, 확정된 공식 규칙으로 코드에 있던 적은 없다. 연안의 30분 규칙(사용자 요청으로 임의 설정,
  §2 근거)을 참고해 하천도 같은 기준(30분)을 쓸지는 **사용자 확인 필요.**

### 2-2. 기존 코드 재사용 범위 / 신규 연결 범위

**재사용**
- `riverStageCriteria`(기준표), `riverTarget`/`riverInfra`(고정 사실)
- `riverFlowProgress`(`types/flow.ts` `FlowProgress`) — 감지→확인→판단→경보→대응→종료 상태를
  표시하는 기존 구조만 재사용한다. 실행 상태 전체를 넣지 않고, 별도 실행 상태에서 현재 단계 표시를 계산한다.
- `riverBrief()`(`leaderBriefs.ts`), `checkConsistency()`(`consistency.ts`) — 이미 `riverFlowProgress`를
  읽는다. 출력 구조는 재사용하되 시점별 등급·이력·종료 조건에 맞게 소비 로직과 검사를 보완한다.
- `scenarios.ts`의 `replaceAll`/`patch`/`patchById` 덮어쓰기 도구 — 새 파서가 만든 값을
  기존 `mockRiver.ts` 표시 구조에 투영할 때 재사용 가능하다. 이 도구 자체에는 React 갱신·창 간 동기화 기능이 없다.

**신규 필요**
- `classifyRiverRisk(flowRatioPercent)` — `riverStageCriteria`의 문자열 범위(20/50/70/100)를
  실제 판정 함수로 만든다. `classifyCoastRisk`/`classifySalinity`와 같은 패턴.
- 시계열 시나리오 파서(별도 파일, `dummyWorkbook.ts`와 다른 모듈) — 여러 시각의 같은 지점 값을
  허용해야 하므로 `서비스+지점+관측시각`을 키로 쓴다(항목ID 중복 금지 로직 재사용 안 함).
- "현재 시험 시점"(playhead)과 이전 시점 대비 지속시간을 계산하는 계층 — 지금 순수 함수 구조에는
  없다. 이게 이번 파일럿의 핵심 난이도.
- 독립된 시나리오 실행 상태와 변경 구독·저장·창 간 동기화 계층 — §2-5 참고.
- 가상 자원 데이터(신규 파일) + `RiverControlPage`/`RiverDispatchPage`의 하드코딩 표를
  실데이터 연결로 교체.

### 2-3. 확정 사항 (2026-09-30, 사용자 결정 — 채팅에서 직접 확인)

이전 버전은 아래 6가지를 미확정으로 남겼다. 사용자가 각 항목을 직접 확인했고, 모두 권장안대로 확정했다.

1. **입력 단위 → Q%(계획홍수량 비율)만 입력.** 수위(m)로 입력받거나 지점별 환산표를 만들지 않는다.
   수위(m)·수위 추세·AI 예보처럼 수위(m) 이력이 있어야 계산되는 파생 지표는 이번 파일럿에서
   **"자료 없음"**으로 표시한다(2-1의 "수위 상승 추세" 행에 해당).
2. **하향 유지시간 → 연안과 동일 30분.** 하천 전용 값을 새로 만들지 않는다.
3. **종료 조건 → "유지시간 충족 + 모든 조치 완료·자원 복귀 확인 + 사용자 종료 확인" 3가지를 모두
   만족해야 종료.** 정상 등급 복귀만으로 자동 종료하지 않는다. 단, **예외 경로로 사용자가 언제든
   수동 강제 종료를 할 수 있게 열어둔다** — 강제 종료 이력은 정상 종료 이력과 구분해서 표시한다
   (재시작/오류 복구용, §2-6의 "재시작·되감기" 정책과 함께 설계).
4. **시험 시간 기준 → 시나리오 시계 기준.** 유지시간·모의 출동/도착 지연은 시나리오 시각으로만
   계산한다. 실제 벽시계 경과시간과 섞지 않는다. 자동 재생 속도는 시나리오 시계의 진행 속도에만
   영향을 준다.
5. **조기경보 입력 범위 → 이번 파일럿에서는 제외.** 수위 이력·강우 관측·강우 예보 입력은 추가하지
   않는다. `riverSuddenRainAlert` 등 조기경보 관련 항목은 Q% 판정과 무관하게 **"자료 없음"**으로
   표시하고, Q%만으로 강우·수위를 역산·추정하지 않는다.
6. **시점 사이 값 처리 → 직전 값 유지.** 다음 관측 시각까지 마지막 관측값을 그대로 유지한다.
   보간이나 공백-초과 시 판정 보류는 이번 파일럿 범위에 넣지 않는다.

이 결정들은 §2-1(입력/자동 구분표)·§2-4(가상 자원)·§2-5(상태 유지)·§2-6(시험 시간·종료 처리)·
§3(구현 순서)의 세부 설계에 그대로 반영해서 진행한다. 아래 표에도 즉시 영향이 있다:

| 영향받는 곳 | 반영 내용 |
| --- | --- |
| §2-1 "수위 상승 추세" 행 | 입력 단위가 Q%뿐이므로 이 행은 "자료 없음, 화면에 표시하지 않음"으로 확정 |
| §2-1 "돌발 강우 조기경보" 행 | 이번 파일럿 범위 제외 확정 — `riverSuddenRainAlert`는 건드리지 않음 |

### 2-4. 가상 인력·장비 (하천 파일럿 최소 범위)

- 신규 파일(가칭 `src/data/mockRiverResources.ts`)에 고정된 소규모 세트만 둔다: 예) 서귀포소방서
  출동차 2대, 현장 통제 인력 4명, 차단기 2개소(돈내코·쇠소깍 각 1). 재현 가능해야 하므로
  매 실행마다 랜덤 생성하지 않고 고정값으로 둔다. 수량·배치 위치는 모두 시험 가정이며 실제 기관 보유량이나
  현장 설치 사실을 뜻하지 않는다. 가상 자원으로 명시하고 실제 연락처·발송 기능을 붙이지 않는다.
- 배치는 "요청 → 사용자 승인 → 모의 출동 → 모의 도착 → 조치 → 복귀/배치 해제"를 최소 흐름으로 제안한다.
  취소도 처리한다. 실제 발송·실제 기관 연동은 하지 않는다. 완료 이력을 미리 생성하지 않는다.
- 자원 목록을 읽을 때의 검증과 **실행 중 배치 검증**을 분리한다. 배치 요청·승인·변경·취소·복귀마다
  가용 수량과 기존 예약/배치를 확인하고 갱신한다. 업로드 시 검사만으로는 이후 중복 배치를 막을 수 없다.
- 예약 시점을 설계에 명시하고, 승인 시 최신 상태로 재검사한다. 동일 요청의 중복 클릭·재수신이
  인원 차감·출동·이력을 두 번 만들지 않도록 요청 식별자로 중복 적용을 막는다.
- 두 창에서 동시에 같은 자원을 요청할 수 있으므로 §2-5의 쓰기 주체·동시 변경 처리도 함께 정한다.

### 2-5. 보드·상세창·새로고침 간 상태 유지 (최소 범위)

새 상태관리 라이브러리는 필수가 아니다. 다만 기존 모듈 객체의 직접 변경만으로 동기화가 되는 것은 아니다.

**기존 설명 정정**

- 같은 페이지의 모듈 객체를 `splice`/`Object.assign`으로 바꿔도 React 재렌더링이 자동 발생하지 않는다.
- 별도로 열린 보드·상세 창은 서로 다른 JavaScript 실행 환경이므로 모듈 인스턴스를 공유하지 않는다.
- 새로고침하면 메모리 상태는 다시 만들어진다. `localStorage` 저장만으로 열린 화면이 자동 갱신되지 않는다.

**최소 설계 제안**

1. 가칭 `RiverScenarioRun`을 별도로 두고 실행 ID·사건 ID·현재 시험시각·지점별 판정 상태·유지시간 추적·
   승인/조치 이력·자원 배치·예약된 모의 응답·변경 버전을 관리한다. 필드는 필요한 범위로 제한한다.
2. `riverFlowProgress`는 `Partial<Record<FlowStep, string>>` 형태의 표시 데이터로 유지한다.
   메타데이터를 여기에 추가하면 기존 `Object.keys(riverFlowProgress).length` 검사 등이 평시에도
   진행 중으로 판단할 수 있다. 독립 실행 상태에서 진행 표시를 파생시키고, 정상 복귀 후 종료 대기나
   종료 이력이 남는 경우도 정합성 검사가 올바르게 처리하도록 기존 '정상=진행 정보 없음' 가정을 재검토한다.
3. 같은 창에서는 변경 구독과 알림을 제공하고, React의 `useSyncExternalStore` 등으로 화면을 갱신한다.
   변경 시 구독자가 인식할 새 스냅샷을 제공한다. 기존 mock 객체 투영은 화면 호환용이며 원본 상태로 중복 관리하지 않는다.
4. 시작·새 창 열기·새로고침 시 저장 상태를 검증해 복원한다. 버전 불일치·손상된 저장값은 명시적으로 안내하며
   조용히 초기화하지 않는다. 기존 수집상태 엑셀 저장 키와 분리한다.
5. 창 간에는 `storage` 이벤트 또는 `BroadcastChannel` 등으로 변경을 전달하고 수신 창의 구독자에게도 알린다.
   `storage` 이벤트는 값을 쓴 창에는 발생하지 않으므로 같은 창의 알림은 별도로 처리한다.
6. 두 창이 각각 과거 상태를 저장해 상대의 승인·배치를 덮어쓰지 않도록 쓰기 주체와 동시 변경 정책을 정한다.
   파일럿에서는 하나의 제어 창이 명령을 순서대로 적용하고 다른 창은 요청을 전달하는 방식도 가능하다.
   변경 버전만 붙이는 것으로 저장 충돌 방지가 완료되는 것은 아니다. 제어 창을 닫았을 때의 중지·재개 방식도 명시한다.
7. 기존 페이지 로컬 승인 상태를 실행 상태의 명령 처리로 연결한다. 카드·지도·브리핑·통합 결재함·보드·
   상세 페이지는 같은 실행 ID와 시험시각의 상태를 사용한다.

### 2-6. 시험 시간과 종료 처리 (추가 설계 제안)

- 기본 조작은 `다음 시점`과 일시정지로 제안한다. 시나리오 시각 기준을 채택하면 대기·새로고침만으로
  유지시간이나 출동시간이 늘어나지 않는다. 자동 재생·배속·재시작 동작은 명시적으로 구분한다.
- '다음 시점'이 여러 중간 시각을 건너뛰더라도 유지시간 도달·모의 도착 등 예약된 사건은 시각 순서대로
  빠짐없이 한 번만 적용한다. 일시정지 중 실제 타이머만으로 모의 도착을 완료시키지 않는다.
- 미래 관측값은 현재 판정과 지속시간 계산에 쓰지 않는다. 보간·결측·긴 관측 공백의 처리 기준은 §2-3에서 확정한다.
- 정상 등급으로 복귀했다고 자동 종료하지 않는다. '종료 가능 여부'와 '종료 승인 완료'를 분리하고,
  유지시간·미완료 조치·자원 복귀 상태를 표시한 뒤 사용자의 종료 확인을 기록하는 방안을 권장한다.
- 재시작·되감기는 기존 승인 이력을 몰래 삭제하거나 미래 이력을 과거 시점에 붙이지 않는다.
  새 실행 ID로 분리하거나 사용자 확인 후 초기화하는 정책을 설계 단계에서 정한다.

### 추가 완료 확인 기준

- 상세 창에서 승인하면 열린 보드·통합 결재함도 새로고침 없이 같은 상태가 되고, 다시 열거나 새로고침해도 복원된다.
- 두 창의 동시 배치 요청, 중복 클릭, 같은 메시지 재수신에도 동일 자원이 이중 배치되거나 이력이 중복되지 않는다.
- 정상 복귀 후 종료 대기·완료 이력을 유지해도 위험등급과 업무 진행 상태를 혼동하지 않고 정합성 검사를 통과한다.
- Q%만 있는 입력으로 수위(m)·강우(mm)가 생성되지 않는다. 근거 없는 조기경보는 자료 없음으로 구분한다.
- 일시정지·다음 시점·배속·새로고침에서 같은 시나리오 시간에 같은 유지시간 판정과 모의 응답 결과를 얻는다.
- 관측 공백과 임계값 경계, 하향 대기 중 재상승, 미래 데이터 미사용을 검증한다.
- 미완료 조치나 미복귀 자원이 있으면 승인된 종료 정책에 맞게 차단·안내하고, 종료 보고는 실제 시험 이력에서 생성된다.
- 기존 수집상태 엑셀과 시나리오를 함께 쓸 때 센서 표시값을 누가 제공하는지 우선순위를 정하고,
  카드·센서·차트가 서로 다른 값을 표시하지 않는지 확인한다. 수집상태를 위험등급으로 변환하지 않는다.
